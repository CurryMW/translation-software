# 定义通用网页的可翻译内容边界

Type: grilling
Status: resolved

## Question

把“可见阅读内容、排除网站 UI/代码/链接/用户名/表单”具体化为可执行的内容边界：文本内容块如何定义、嵌套节点如何去重、短文本/混合语言/隐藏文本/Shadow DOM/iframe/虚拟列表如何处理，以及哪些场景明确不保证支持？

## Follow-up questions

上一轮已确认：按语义块翻译；包含标题、正文、列表项、帖子、评论、图片说明和引用；所有链接文字均排除；处理已显示或即将进入视口的内容；尽力支持开放 Shadow DOM 与权限允许的 iframe；排除表单和可编辑区域；首版以通用规则为主。

仍需确认以下边界：

1. 嵌套节点出现父子文本重叠时，是否只选最外层可独立阅读块，避免父块和子块重复翻译？
2. 少于多少字符的文本默认跳过？是否跳过纯 emoji、纯数字、纯标点和单个词？
3. 混合中外文文本如何判断“值得翻译”？是否要求外文字符占比达到阈值？
4. 去重身份是否允许使用 DOM 节点生命周期内的弱身份（节点引用 + 原文哈希），而不承诺跨刷新稳定？

## Answer

- 翻译单位是按语义组织的、可独立阅读的文本内容块，不按视觉行或任意文本节点拆分。
- 默认纳入标题、正文、列表项、帖子、评论、图片说明和引用；导航、工具栏、按钮、菜单、页脚、广告、表单及可编辑区域排除。
- 所有链接文字一律排除，即使它们是新闻标题或帖子标题；这是本 MVP 的明确取舍。
- 折叠、`aria-hidden`、`display:none` 等内容不可直接提交翻译；可见范围已由用户在 [动态网页契约的最新反馈](05-dynamic-processing.md#最新用户反馈) 中收紧，原“即将进入视口”预译建议不再生效。
- 父子节点文本重叠时只选择最小且完整的语义块，避免父块与子块重复翻译。
- 纯数字、纯标点、纯 emoji 默认跳过；正常外语短语不因字符数或词数过短而跳过。
- 混合语言文本仅在非目标语言字符约占 30% 或以上时提交翻译；该阈值可在验收阶段根据样本调整。
- 尽力支持普通 DOM、开放 Shadow DOM 和权限允许的 iframe；不承诺关闭 Shadow DOM、Canvas 文字、图片文字和浏览器 PDF 阅读器。
- 当前页面生命周期内以 DOM 节点引用加规范化原文哈希去重；节点文字变化时重新翻译，刷新后不保留身份或译文缓存。
- 首版采用通用识别规则，不预先为具体网站编写专属适配器；适配器只在真实失败案例出现后新增。
