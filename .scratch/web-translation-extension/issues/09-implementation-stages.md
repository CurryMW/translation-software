# 划分 MVP 实现阶段与集成顺序

Type: grilling
Status: resolved
Assignee: Curry学长（Codex 协作）
Blocked by: 08

## Question

在翻译服务、内容边界、呈现契约、语言策略、动态处理、凭据隐私、失败成本和验收门槛均已确定后，如何划分可独立验证的实现阶段与集成顺序？需要明确每阶段的可运行切片、依赖关系、不可跨越的安全前置条件，以及何时接入真实百度 API。

## Comments

### 第一轮：阶段原则（已确认）

用户确认全部采用推荐方案：

1. 以可运行的纵向切片组织阶段，每阶段贯穿页面识别、呈现、消息与测试。
2. 先建立统一翻译服务适配器并使用确定性 Mock，之后再接百度。
3. 真实百度请求前必须通过密钥隔离、最小化请求、字符预算、错误分类和日志脱敏检查。
4. 先完成当前可视静态内容，再独立加入动态新增、原文更新、切入确认与过期结果保护。
5. 设置页保存凭据；首次启用某域名时申请对应权限；切入已开启网站时先确认。
6. 自动化默认使用 Mock；真实百度只做人工触发、低额度的固定文本烟囱测试。
7. 每阶段通过本地夹具回归、相关隐私/成本检查和最小人工验收后才能进入下一阶段。

### 第二轮：具体阶段与边界

❓ **Q8 - 阶段数量与顺序**：采用哪条具体实现路线？

- A：三个大阶段——基础功能、动态网页、真实接口；文件少，但错误容易跨模块堆积。
- B：六个可运行阶段——扩展骨架与安全存储；静态可视内容 Mock 闭环；语言/队列/失败状态；动态网页生命周期；百度真实适配器；真实网站加固与总验收。
- C：按每个技术模块拆成十几个阶段；粒度细，但个人 MVP 协作和验收成本偏高。

➡️ 推荐 B。六阶段既能隔离风险，又不会把个人项目拆得过碎；每个阶段都产出可加载的扩展版本。

➡️ 推荐 B。类型可以保护消息协议、任务状态和适配器结果；当前 UI 很小，引入 React 只会增加包体、样式隔离和调试成本。

❓ **Q10 - 可替换服务边界**：首版为未来 DeepL 或其他服务预留多少结构？

- A：只写百度专用流程，未来再重构。
- B：现在定义最小统一适配器接口，但首版只实现百度，设置页不展示未实现供应商。
- C：首版同时实现百度和 DeepL。

➡️ 推荐 B。保留可替换边界，但不为未交付能力增加界面、测试和凭据风险。

❓ **Q11 - 真实密钥介入点**：真实百度烟囱测试如何进行？

- C：暂时跳过真实接口验证，交付后再尝试。

➡️ 推荐 B。这是明确的人机检查点；在安全门通过前，开发流程既不需要也不应接触真实密钥。

❓ **Q12 - 阶段失败规则**：某阶段未通过时是否继续开发后续阶段？

- A：继续开发，最终一起修复。
- B：阻断依赖它的后续阶段，只允许修复当前阶段或推进与失败无依赖的准备工作。
- C：仅隐私问题阻断，其余问题最后处理。

➡️ 推荐 B。尤其是静态内容识别、状态一致性和安全门失败时，继续叠加动态处理或真实 API 只会放大问题。

❓ **Q13 - 每阶段交付物**：什么证据表明一个阶段完成？

➡️ 推荐 B。证据不保存正文和密钥，只记录通过项、耗时、错误类别和测试环境。

### 技术栈修订

用户随后明确把 Q9 改为 C：采用 TypeScript + React，以方便后期调整 UI。React 的职责限定为 popup、设置页和网页内译文/提示组件；内容发现、任务状态、消息协议、翻译服务适配器、百度签名与 service worker 保持为与 React 无关的纯 TypeScript 模块。网页内多个译文位置应共享统一的 React 渲染协调层，避免为每个文本内容块创建互不关联的应用实例。

## Answer

MVP 采用 TypeScript + React 和受控的最小前端构建链；React 只负责 popup、设置页及网页内可见组件，核心翻译与浏览器扩展逻辑保持为纯 TypeScript。整体以六个严格顺序、可加载运行的纵向切片推进。每个阶段必须提供可加载产物、自动测试结果和相应人工检查表，未通过时阻断依赖阶段。

### 阶段一：扩展骨架与安全控制面

- 建立 Manifest V3、service worker、content script、React 弹窗、React 设置页和类型化消息协议，并明确 UI 层与纯 TypeScript 核心层的依赖方向。
- 安装时不申请全站权限；首次启用网站时才申请对应域名权限。
- 建立本机设置存储、清除流程以及 `chrome.storage.local` 的可信扩展上下文访问限制。
- 使用假凭据验证保存、替换和清除；本阶段禁止真实翻译请求。

完成证据：扩展可通过“加载已解压的扩展程序”启动，权限和存储检查通过，页面与 content script 无法读取假密钥。

### 阶段二：静态可视内容的 Mock 闭环

- 在可控静态夹具中完成“启用网站—扫描当前可视语义块—Mock 翻译—原文下方呈现”的完整路径。
- 落实链接、网站 UI、代码、表单和隐藏内容排除规则，以及节点加规范化原文哈希去重。
- 使用统一 React 渲染协调层实现紧凑双语样式、加载状态、收起和单块重试的基础呈现，避免每个文本内容块各自创建完整 React 应用；验证浅色/深色页面及样式隔离。

完成证据：无需真实 Key 即可反复运行固定输入/输出回归；不得出现错位、重复插入或页面结构破坏。

### 阶段三：任务编排、语言与失败成本

- 在统一翻译服务适配器后继续使用确定性 Mock，并加入可编排的正常、超时、限流和确定性错误响应。
- 实现源语言识别、网站目标语言、单块手动源语言、同语言跳过、长文本切分合并、套餐感知队列、有限重试、页面内缓存和本地字符预算。
- 实现块级失败与供应商级顶部提示，确保日志只记录脱敏类别信息。

完成证据：所有成功与失败状态都能用 Mock 稳定复现，取消和预算停止后不再产生新任务。

### 阶段四：动态网页生命周期

- 加入仅针对实际可视区域的观察与扫描，处理滚动新增、异步插入、原文更新、SPA 导航、开放 Shadow DOM 和获准 iframe。
- 实现文字稳定等待、标签页切入确认、后台暂停、拒绝后停止新增任务，以及页面/节点/原文/语言/供应商版本联合校验，禁止过期结果回写。

完成证据：动态夹具持续滚动和内容替换时无重复、错位或过期译文，切换标签页和关闭翻译可可靠停止后续提交。

### 阶段五：百度真实适配器

- 保持最小统一适配器接口，首版只实现百度；不展示 DeepL 等未实现供应商。
- 仅由 service worker 读取 APPID 与密钥、计算签名并请求百度；映射语言、长度、QPS、错误码和预算策略。
- 真实请求启用前必须通过：凭据隔离、最小化请求、字符预算、错误分类、超时/重试和日志脱敏测试。
- 自动化仍使用 Mock；用户只在已加载扩展的设置页自行输入真实凭据，凭据不得进入聊天、仓库、测试快照或命令输出。

完成证据：用少量固定无敏感文本完成人工触发的真实烟囱测试，并只保留脱敏的通过项、耗时、错误类别和测试环境记录。

### 阶段六：真实网站加固与总验收

- 对 X、英文 Wikipedia、GitHub Issue/Discussion、Hacker News 及本地夹具执行完整回归。
- 执行 30 个样本的集成完整性与可读性检查、10 分钟连续滚动、时延/扫描/内存预算和隐私阻断检查。
- 依据既定不支持边界记录可延期问题，形成最终可加载构建产物和使用说明。

完成证据：满足「定义跨网站 MVP 验收标准」中的全部阻断门槛；任何核心样本失败、凭据泄露、误发内容或页面破坏均不得交付。

### 依赖与停止规则

六阶段原则上顺序推进。某阶段失败时，只允许修复当前阶段或进行与失败项无依赖的准备工作，不进入依赖它的后续阶段。真实百度接口是单独安全门：阶段一至四可以完全依靠 Mock 完成，在安全门全部通过前不发送任何真实正文。
