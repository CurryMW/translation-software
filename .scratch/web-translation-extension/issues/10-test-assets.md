# 设计 MVP 测试资产与验证方法

Type: grilling
Status: resolved
Assignee: Curry学长（Codex 协作）
Blocked by: 08, 09

## Question

为已确定的 MVP 放行门槛设计可重复的自动化测试、可控本地测试夹具、百度 API 模拟响应、真实网站人工检查表和性能采样方法；明确哪些断言必须自动化、哪些必须人工完成，以及如何避免真实 API 测试造成意外调用成本。

## Comments

### 口径修正

设计隐私测试时发现先前“网络请求只含正文和语言参数”的表述遗漏了百度通用翻译的必需鉴权字段。已修正为：只发送当前文本块以及 `q`、`from`、`to`、`appid`、`salt`、`sign`；密钥本身和签名原串绝不发送，也不发送整页、页面 URL、标题、账号名或相邻上下文。

### 第一轮：测试边界与资产原则

❓ **Q1 - 测试接缝**：自动化测试应从哪些公开界面观察行为？

- A：直接测试大量私有函数和 React 内部状态。
- B：固定五个行为接缝——页面内容发现、翻译会话状态、翻译供应商适配器、Chrome 扩展运行链路、用户可见 React UI。
- C：只做完整浏览器端到端测试。

➡️ 推荐 B。测试与真实调用者跨越同一接缝，不依赖私有函数、内部调用次数或 React 组件树；这样重构实现时，只要可观察行为不变，测试就不应破裂。

❓ **Q2 - 自动与人工的分界**：什么必须自动化？

- A：包括真实百度和真实网站在内全部自动化。
- B：确定性的内容规则、状态转换、错误/预算、消息与存储、权限、UI 交互和本地浏览器闭环自动化；真实站点适配、视觉融合、译文语义、真实百度凭据与内存体感人工检查。
- C：仅做少量单元测试，其余人工点击。

➡️ 推荐 B。外部网站和翻译服务会变化，强行自动化会制造脆弱测试或意外费用；核心行为必须可重复自动回归。

❓ **Q3 - 本地网页夹具**：如何组织可控测试页面？

- A：把所有场景堆进一张巨大测试页。
- B：建立场景索引，加多个聚焦页面：静态文章与排除项、浅/深主题、动态信息流、原文改写与乱序响应、开放 Shadow DOM、同源/跨域 iframe 权限边界。
- C：保存真实网站 HTML 副本。

➡️ 推荐 B。一个页面只表达少量行为，失败时容易定位；不复制真实网站内容，也避免夹具随站点结构失效。

❓ **Q4 - 百度模拟方式**：怎样模拟成功、限流和失败？

- A：全局劫持 `fetch` 并按 URL 写复杂条件。
- B：在供应商接缝注入脚本化 Fake Adapter，可按固定顺序返回成功、慢响应、超时、限流、鉴权失败、余额/配额耗尽、乱序和取消；另用独立传输契约测试检查百度请求字段与错误映射。
- C：所有测试永远返回同一句中文。

➡️ 推荐 B。只模拟系统外部边界，不模拟自己的队列和状态模块；期望译文使用人工写定的固定值，避免测试按实现算法重新计算答案。

❓ **Q5 - 真实网站验收**：X、Wikipedia、GitHub 和 Hacker News 是否采用稳定选择器自动化？

- A：为每个网站维护自动选择器。
- B：使用统一人工检查表，记录日期、Chrome 版本、网站类型、权限状态、发现/翻译/排除/重复/页面破坏结果，不保存账号信息或正文；本地夹具承担自动回归。
- C：只人工检查 X。

➡️ 推荐 B。真实站点 DOM、登录状态和实验版本不可控，选择器自动化维护成本高；四类样本仍必须全部人工通过核心路径。

❓ **Q6 - 真实百度调用成本**：烟囱测试如何硬限制费用？

- A：每次自动测试都调用真实百度。
- B：默认完全禁用真实调用；设置页提供明确的人工烟囱测试，一次只使用预置、无敏感、总计不超过 300 个源字符的固定文本，提交前显示字符数并二次确认，烟囱测试不自动重试。
- C：使用任意当前网页正文测试，只依赖月度预算。

➡️ 推荐 B。它验证凭据、签名、接口地址和响应结构，同时把一次操作的最大字符数在请求前固定下来。

❓ **Q7 - 性能测量**：如何验证扫描 P95、内存和滚动稳定性？

- A：全部凭主观感受。
- B：本地动态夹具自动记录扫描耗时、请求数、队列深度、DOM 插入数并计算中位数/P95；再在 X 上人工连续滚动 10 分钟，通过 Chrome DevTools/任务管理器记录扩展前后内存与明显卡顿。
- C：尝试把所有性能指标做成硬性端到端测试。

➡️ 推荐 B。确定性计数和耗时适合自动化；真实站点内存与卡顿受网络、页面自身和浏览器版本影响，需要保留环境信息后人工判断。

❓ **Q8 - 测试证据中的隐私**：测试报告保存什么？

- A：保存真实网页截图、正文、请求和响应，便于复盘。
- B：只保存测试名称、通过/失败、耗时、计数、脱敏错误类别、浏览器/扩展版本和人工备注；截图只允许来自本地固定夹具，真实网站不保存正文或账号画面。
- C：完全不保存结果。

➡️ 推荐 B。证据足以复现行为，同时不把浏览记录和翻译内容变成新的持久数据源。

### 官方工具事实

当前官方文档调研记录见 [TypeScript + React 的 Chrome MV3 扩展测试工具边界](../../../research/extension-test-tooling.md)。关键约束：Vitest/Node 适合纯 TypeScript，React Testing Library + jsdom 适合用户可见组件行为但没有真实布局和扩展能力；真正的 MV3 自动化需要 Playwright `launchPersistentContext`、隔离临时 profile、随附 Chromium 和已构建的 `dist/`。Google Chrome/Edge 已移除 Playwright 扩展文档所依赖的命令行侧载路径，因此当前正式版 Chrome 仍需人工加载验收。

### 第二轮：工具、版本与提交门槛

❓ **Q9 - 最小测试工具组合**：选择哪套分层工具？

- A：只用 Vitest，在 jsdom 中模拟全部浏览器行为。
- B：Vitest/Node 测纯 TypeScript；Vitest + React Testing Library + jsdom 测 React 行为；Playwright + 随附 Chromium + `dist/` 测真实 MV3 链路；当前 Chrome Stable 人工验收。
- C：所有测试都使用 Playwright。

➡️ 推荐 B。三层分别覆盖快速逻辑、UI 行为和真实扩展能力，避免让 jsdom 假装拥有布局/Chrome API，也避免所有小测试都承担浏览器成本。

❓ **Q10 - Vitest Browser Mode**：首版是否额外引入浏览器组件测试层？

- A：首版不引入；真实布局问题直接交给 Playwright 扩展 E2E，只有出现明显测试缺口时再加。
- B：从第一阶段同时维护 jsdom、Browser Mode 和 Playwright 三套浏览器测试。
- C：用 Browser Mode 替代 Playwright 扩展 E2E。

➡️ 推荐 A。Browser Mode 能补真实布局，但不是已加载 MV3 扩展上下文；首版同时维护它和 Playwright收益不足，C 也无法覆盖权限、service worker 和 content script 链路。

❓ **Q11 - Chrome 120+ 的证据表述**：最低版本如何写才不夸大？

- A：只要最新 Chromium 通过，就声明“所有 Chrome 120+ 已验证”。
- B：声明 `minimum_chrome_version` 与所用 API 以 120 为设计兼容下限；仅把实际人工运行过的当前 Chrome Stable 标为已验证；以后若取得 Chrome 120 环境再补运行证据。
- C：放弃最低版本，永远只写当前 Chrome。

➡️ 推荐 B。安装下限和实际测试覆盖是两件事，不能互相替代。

❓ **Q12 - 自动测试执行位置**：个人 MVP 是否立即搭建云端 CI？

- A：先提供统一的本地命令，并将其作为每阶段阻断门槛；仓库接入远程托管后再复用同一命令建立 CI。
- B：现在就建立 GitHub Actions，即使仓库尚无远程协作需求。
- C：只由开发者临时运行零散命令。

➡️ 推荐 A。可重复命令是核心资产；云端平台不是个人本地 MVP 的前置条件。

❓ **Q13 - 开发测试节奏**：自动化是在功能之后补，还是逐行为推进？

- A：每个行为切片先写一个从已确认接缝观察到的失败测试，再写最小实现使其通过，继续下一行为。
- B：每阶段功能全部完成后统一补测试。
- C：先写完整测试库，再一次性实现全部功能。

➡️ 推荐 A。逐个 red → green 的纵向切片能避免测试想象中的内部结构；重构放在阶段评审，不混入每个最小实现循环。

❓ **Q14 - 覆盖率门槛**：用什么判断自动测试“足够”？

- A：要求 100% 行覆盖率。
- B：关键行为矩阵必须 100% 通过；代码覆盖率只作为发现盲区的参考，不作为唯一放行门槛。
- C：只要整体行覆盖率超过 60% 即可。

➡️ 推荐 B。覆盖率高不等于验证了取消、乱序、误发正文或权限失败；关键场景缺一个都不能用无关代码覆盖率补偿。

❓ **Q15 - MV3 端到端环境**：Playwright 如何加载扩展？

- A：每次用干净临时 persistent profile，以随附 Chromium 加载实际 `dist/`，动态取得扩展 ID，并覆盖 service worker 挂起后恢复。
- B：复用用户日常 Chrome profile，避免每次配置。
- C：直接打开源码页面，不构建扩展。

➡️ 推荐 A。复用日常 profile 既不受 Playwright支持又会污染个人数据；只打开源码页面无法证明 manifest、权限、content script 和 service worker 真正协作。

❓ **Q16 - 固定文本语料**：30 个质量与完整性样本如何组成？

- A：全部是普通英文长段落。
- B：18 个英文正文/帖子/评论，4 个中英混合语言块，4 个英文长文本/换行/特殊字符块，以及 2 个日语、1 个韩语、1 个西班牙语块；另设不计入 30 个译文样本的排除语料。

❓ **Q17 - 视觉回归**：是否用截图作为自动阻断项？

- A：对所有真实网站做整页截图比较。
- B：只对本地夹具中的 popup、设置页、页内译文及提示状态做小范围截图基线，覆盖浅色/深色和典型长文本；任何基线更新必须人工审阅。
- C：完全不做截图回归。

➡️ 推荐 B。它能发现 React UI 和样式隔离回归，又不会被真实网站广告、时间线和字体变化制造大量误报。

❓ **Q18 - 四个真实网站的通过规则**：怎样判定核心路径通过？

- A：每个网站看到一条译文即可。
- B：每站至少检查 5 个应翻译内容块和主要排除区域；验证授权、切入确认、加载/成功/失败、滚动新增、无重复、关闭停止及页面不破坏。任一站核心路径失败都阻断 MVP。
- C：只要求 X 严格通过，其余仅记录。

➡️ 推荐 B。此前已把四类真实样本列为必测对象，不能在测试实现阶段暗中降低门槛。

❓ **Q19 - 测试失败与不稳定测试**：失败时如何处理？

- A：自动重试到通过，避免影响进度。
- B：默认不靠重试掩盖失败；先保存脱敏错误和环境信息，再区分真实回归、测试缺陷或外部站点变化。核心本地测试不得跳过或隔离后放行。
- C：偶发失败直接忽略。

➡️ 推荐 B。外部站点变化可以按后续兼容性规则分级，但本地关键行为失败必须修复。

❓ **Q20 - 一键验证入口**：开发阶段如何避免漏跑某一层测试？

- A：开发者自行记住多条命令。
- B：提供一个不访问真实百度和真实网站的统一本地 `verify` 入口，依次执行类型检查、构建、单元/React 测试和本地 Playwright 扩展 E2E；真实百度与四站检查保持为显式人工验收。
- C：把真实百度和 X 也放进一键验证。

➡️ 推荐 B。一键入口必须默认零真实调用、零第三方站点依赖，人工检查不会被误触发。

## Answer

MVP 建立四层验证体系：Vitest/Node 纯逻辑测试、Vitest + React Testing Library/jsdom 的 React 行为测试、Playwright 随附 Chromium 中加载真实 `dist/` 的扩展端到端测试，以及当前 Google Chrome Stable 中的人工验收。测试通过已确认的行为接缝观察结果，不测试私有函数、内部调用次数或 React 组件树。

### 自动化层级

1. **纯 TypeScript 行为**：使用 Vitest/Node 验证文本规范化与排除、语言规则、状态机、任务队列、并发/重试/退避、长文本切分与有序合并、页面内复用、字符预算、错误映射和过期结果判定。
2. **React 用户界面**：使用 Vitest + React Testing Library + jsdom，按角色、标签、可见文本和用户操作验证 popup、设置页、页内译文、切入提示、加载/成功/失败/收起/重试状态及基本键盘可访问性；`chrome.*` 通过注入的最小端口模拟。首版不额外维护 Vitest Browser Mode。
3. **真实扩展链路**：使用 Playwright 的隔离临时 persistent context、随附 Chromium 和实际构建的 `dist/`，动态取得扩展 ID，验证 manifest、扩展页、content script、service worker、消息、存储、权限、静态/动态 DOM、可视区域、开放 Shadow DOM、获准 iframe 和 worker 休眠恢复。
4. **人工验收**：在当前 Chrome Stable 中加载同一个 `dist/`，验证浏览器工具栏入口、原生权限提示、站点访问撤销、视觉融合、真实网站、真实百度烟囱测试、10 分钟滚动与内存体感。

`minimum_chrome_version: "120"` 只作为经 API 可用性核对的设计兼容下限；Playwright Chromium 和当前 Chrome Stable 通过不能表述为所有 Chrome 120+ 版本均已实测。

### 固定测试资产

- 场景索引，以及分别聚焦静态文章/排除项、浅色/深色、动态信息流、原文改写/乱序响应、开放 Shadow DOM、同源与跨域 iframe 权限边界的本地页面；不复制真实网站 HTML。
- 脚本化 Fake Translation Adapter，可按测试指定顺序返回成功、慢响应、超时、限流、鉴权失败、余额/配额耗尽、乱序和取消结果。它只替代外部供应商，不替代项目自己的任务模块。
- 百度传输契约样本，使用固定输入检查 POST 字段 `q`、`from`、`to`、`appid`、`salt`、`sign` 和响应/错误映射；不得包含真实密钥，预期值必须由人工写定，不能用被测实现重新计算。
- 30 个固定人工质量与集成样本：18 个英文正文/帖子/评论、4 个中英混合块、4 个英文长文本/换行/特殊字符块、2 个日语块、1 个韩语块、1 个西班牙语块。链接、UI、代码、表单、隐藏内容等排除语料另建集合，断言其不产生翻译任务。
- 本地 UI 截图基线只覆盖 popup、设置页、页内译文及提示的关键状态、浅色/深色和典型长文本；不对真实网站做整页截图。任何基线更新必须人工审阅。

### 真实网站人工检查

X、英文 Wikipedia、GitHub Issue/Discussion 和 Hacker News 各至少检查 5 个应翻译内容块和主要排除区域，并验证：首次授权、切入确认、加载/成功/失败、滚动新增、原文变化、无重复、关闭后停止请求以及页面布局/交互未被破坏。四个样本任一核心路径失败都阻断 MVP；具体处置交由后续兼容性票据判定。

检查表只记录日期、Chrome/扩展版本、网站类型、权限状态、通过项、数量、脱敏错误和人工备注，不保存账号、真实正文、译文、完整网址或真实网站截图。

### 性能验证

- 本地动态夹具自动记录扫描耗时、请求数、队列深度和 DOM 插入数，计算中位数与 P95，并验证静止后没有持续扫描/请求。
- 当前 Chrome Stable 中在 X 人工连续滚动 10 分钟，使用 DevTools 或 Chrome 任务管理器记录测试环境、扩展前后内存和明显卡顿；目标沿用扫描 P95 不超过 100ms、扩展内存增量不超过 50MB、无重复译文或失控请求。
- 真实站点性能受页面、网络和浏览器版本影响，失败必须先分类，不能自动归因给扩展或直接忽略。

### 真实百度烟囱测试

默认构建、测试和统一验证命令均禁止访问真实百度。只有通过真实服务安全门后，用户才能从设置页显式发起烟囱测试：使用内置无敏感固定文本，总源字符不超过 300；提交前显示字符数并二次确认；不自动重试。真实 APPID 与密钥仅由用户在扩展设置页输入，不进入仓库、聊天、命令输出、快照或报告。

### 放行与命令

- 开发遵循行为接缝上的红—绿纵向循环：一个失败行为测试、最小实现、通过后再进入下一个行为。
- 提供统一的本地 `verify` 入口，依次运行类型检查、构建、Vitest 纯逻辑/React 测试和本地 Playwright 扩展 E2E；该入口零真实 API 调用、零第三方网站依赖。
- 所有关键行为矩阵必须 100% 通过；代码覆盖率只用于发现盲区，不以全局百分比替代行为门槛。
- 测试失败默认不靠重试掩盖。先保存脱敏错误与环境信息，再分类为代码回归、测试缺陷或外部站点变化；核心本地测试不得跳过、隔离后放行。
- 测试证据只保存测试名、结果、耗时、计数、脱敏错误、浏览器/扩展版本和人工备注；截图仅来自本地固定夹具。
